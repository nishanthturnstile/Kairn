# Design System: Kairn — Open atlas

## Overview

**Creative North Star: "Open atlas"**

Chronology makes a remembered journey understandable. Open atlas keeps time and place beside photographs, personal accounts and dated practical details. Mineral canvas, white surfaces, deep blue actions and slate text give the content a calm frame; Newsreader supplies the reading voice and Instrument Sans keeps controls precise.

Each composition serves its task: account forms follow a narrow sequence, the workspace groups edits and permissions, and the reader places a chapter spine beside focused content. Rest days, transfers and unknown locations belong in the same chronology. Essential labels stay outside photographs, and missing route evidence remains a visible gap.

This contract merges the implemented component system into the selected Open atlas direction. It does not close the DS01–DS12 plan or establish native runtime acceptance. The product requirements, application design and implementation records retain authority over behavior, permissions and acceptance.

The complete-redesign brief of 4 November 2026 replaces the P02 photographic-journal direction. See the [audit, research, architecture and acceptance](docs/implementation/experience_redesign.md), [direction studies](docs/implementation/experience_directions.html), [detailed redesign plan](docs/implementation/design_system_redesign_plan.md), and [component guide and migration ledger](docs/implementation/design_system_catalog.md). [PRODUCT.md](PRODUCT.md) indexes the confirmed product context; [product requirements](docs/core/product_requirements.md) and [application design](docs/core/application_design.md) govern.

**Key Characteristics:**

- Chronology with explicit dates, pauses and unknown locations.
- Calm broad surfaces with precise, small-corner controls.
- One semantic light/dark system with platform-owned components.
- Visible labels, stable action names and adjacent source context.

## Colors

The palette is mineral and cool: blue provides action emphasis, slate provides reading contrast, and restrained semantic pairs explain feedback and review.

### Primary

Deep blue is the light appearance's action voice; pale blue takes that role against dark surfaces. Use `action` with `onAction` for filled controls, `actionHover` where the adapter supplies it, and `selected` with readable text for the current choice. Selected state must remain visibly different from keyboard focus.

### Neutral

`canvas` is the page ground; `surface` holds focused content and controls; `elevated` is available for a layer. `text` and `muted` carry emphasis. Use `border` for visible control boundaries and `divider` for quiet section separation. `scrim` explains a modal layer.

### Semantic states and appearances

Danger, warning, success, information and review each have a foreground and surface role. Review is its own meaning, not generic success or publication approval. Pair color with specific text, state semantics or a pattern.

The frontmatter captures the shared light/dark mappings from `packages/design-tokens/src/index.ts`. Component entries show the web light treatment; adapters select the corresponding active-appearance roles. Do not use a light foreground with a dark background arbitrarily.

Default appearance follows the device. Explicit Light/Dark preference persists per browser origin in localStorage and per native installation in SecureStore, independently of authentication. Restricted storage leaves an in-memory session preference. Web initializes before React mounts; native resolves the preference before rendering the navigator. Changing appearance preserves work, actor and selected chapter. Photographs keep their original pixels; surrounding labels and fallback surfaces adapt. Native runtime behavior still requires device qualification.

**The Semantic Role Rule.** Choose a semantic role for meaning, map it in both appearances, and let the platform adapter apply it. Do not add screen-level color literals or new consumers of legacy palette aliases.

## Typography

**Display Font:** Newsreader, with Georgia/serif on web.
**Body Font:** Instrument Sans, with system-ui/sans-serif on web.

Newsreader gives titles, day markers and selected reading moments an editorial voice. Instrument Sans carries prose, instructions, values, metadata and controls. Do not turn routine form labels into display typography.

### Hierarchy

The frontmatter records the shared desktop and mobile scale: display, page title, section title, card title, body, compact body, label and metadata. `control` records the current common button text treatment. These are role defaults, not a requirement to give every surface a display heading. Web reader compositions also use responsive title sizing and a larger reading body; account forms keep their task hierarchy.

Use regular for prose, semibold for controls and labels, and the available editorial medium/semibold weights for journey titles. Long titles wrap. Keep reading text within a comfortable measure; the current web reader uses a narrower prose column than the overall reading surface. Numeric day markers use tabular figures on web.

Native loads Newsreader500/600 and InstrumentSans400/500/600/700 once at the root. The platform maps these named files to the shared roles; it must not synthesize missing weights.

**The Two Voices Rule.** Use Newsreader for expressive journey titles and Instrument Sans for instructions, controls and prose. Use the bundled native weight names rather than synthetic bold.

## Layout

Use the shared four-point spacing scale. Compact layouts start at the smallest viewport; medium begins at 768 CSS px and wide at 1200 CSS px. The shared grid describes four/eight/twelve columns, with responsive margins and gutters, a page maximum of 1280px and reading containers of 640–720px. Actual task layouts may occupy fewer columns; prose stays at or below 70ch.

Horizontal web navigation replaces the permanent sidebar. Discover presents one editorial journey entry per event with useful filters. Your journeys owns create/join/revisit. The reader preserves chapter selection while switching Story, Explore and Learn; wide layouts place chronology beside content, while compact/native layouts present a chapter grid and one focused content view. An account form is a sequential task, not a miniature reader or new hero.

Use broad surfaces and section dividers; avoid nested card grids. Let text, controls and grouped actions wrap without clipping. Safe areas, keyboards, system back and text scaling are platform requirements, not reasons to remove content or reduce targets.

Media currently adapts by composition: web editorial covers use 4:3, the compact reader uses 16:9, and native media uses 3:2. Shared ratio tokens are a reserved contract and are not yet universally applied. Keep titles and essential labels outside media, preserve meaningful captions, and retain a text route when media is missing or fails.

## Elevation & Depth

Canonical buttons, fields, chapter rows and practical details are flat. Surface tone, boundaries, spacing and a modal scrim establish hierarchy. This is not a claim that every legacy surface has been migrated; incidental legacy shadows do not define a new component rule.

**The Layer With Purpose Rule.** Use a surface, divider or scrim to explain grouping and layers. Do not add elevation merely to decorate routine controls or chapter rows.

## Shapes

Controls have precise small corners. Media and modal layers use medium corners; larger content surfaces may use the large radius. Circular radios and avatars, and compact rounded status badges, retain their purpose-specific shapes. Do not apply a pill silhouette to ordinary actions or impose one radius on every component.

Web controls have a minimum 44 CSS px target; native controls use a minimum 48dp. These are minimums, never fixed text-clipping heights. Icon controls need an accessible name and the same target floor. Use the shared thin border for boundaries. Focus is visible and distinct from selected/pressed state; native pressed feedback answers the interaction need served by web hover.

## Components

The canonical implementations live in `apps/web/src/components/ui` and `apps/mobile/src/components/ui`. Share plain values, action emphasis, state meaning and variant names; keep DOM and Unistyles rendering separate. Existing shadcn/Radix and native semantics remain intact. Compatibility wrappers delegate to these controls; their consumers and removal gates stay in the migration ledger.

### Buttons

Use `primary` for the task's main commitment, `secondary` for a bordered alternative, `quiet` for reversible supporting actions and `destructive` for an action whose impact is explained. Strong fills should communicate importance, not decorate every action.

Both platforms retain the label while pending, expose busy state and prevent repeat activation. Web adds a dashed busy boundary; native shows a platform progress indicator. Disabled state is visibly subdued. Web hover and native pressed feedback are platform adaptations. Existing default/outline/ghost names are compatibility aliases, not new variant guidance. Navigation keeps link semantics; form submission is explicit.

### Inputs / Fields

Field anatomy is visible label, control, then associated help or error. Mark optional fields plainly. Put error meaning in text and associate it with the field; preserve user input after failure. Web uses IDs/descriptions and existing validated account field APIs; native supplies the label and hint while retaining account refs and focus callbacks.

Inputs and TextArea use the surface, control boundary and small control radius. TextArea has a minimum initial size and supports multiline content. Read-only and disabled are different states. Do not use a placeholder as the only label.

### Selection and navigation

Use platform select/picker, checkbox and radio semantics. The entire choice row is reachable; selected text stays visible. The reader's segmented selection uses radio behavior on web and explicit selected semantics on native. Route navigation remains links. Native pickers have scrollable options, a visible Cancel action and system-back dismissal.

### Notices and status

Keep feedback near the action or content it qualifies. Review, source audience and publication eligibility remain distinct. Critical failures and restriction receipts persist rather than disappearing into a transient toast. Loading states describe actual work; do not invent percentages.

### Cards / Containers

Use a surface when it groups a task or focused content, with the established radius and padding. Prefer a divider and vertical rhythm for routine chapter/practical rows. A collection does not require a grid of individually elevated cards.

### Dialogs

Web confirmation uses the browser modal layer, safe Cancel focus, Escape, protected focus and trigger return. Native uses a platform Modal with Cancel/back behavior and focus requests. Native focus, keyboard, back and screen-reader behavior remain awaiting compiled-device acceptance. No transition is required to understand a dialog.

Moment details use the same overlay owner with `fullScreen` and an explicit `closeLabel`. The body scrolls independently of the heading and Close action; web makes that body keyboard-focusable. Native uses a full-screen Modal within safe-area insets. Photo details contain the whole image rather than cropping it. This source implementation does not establish native runtime acceptance.

### Journey content

ChapterNavigation keeps day, date, title, activity and selected state together. Include rest days and unknown locations in sequence. PracticalDetail keeps the observation/value, date, contributor and source action adjacent. Media keeps title/caption separate and falls back to text on failure. These components accept data and actions; fixture content belongs in catalog/controller code.

JourneyTimeline preserves caller order, explicit unknown time/timezone/location, evidence and parallel-account labels. Selection filters a collection; this component does not infer chronology or reorder a story. MomentGallery receives only a bounded, already-permitted projection. It mounts media only for an explicitly opened item, derives the viewer from the current collection and removes its content when that item is absent. Keep source owner and photographer/credit separate, and label capture time and entry time independently. SourceScopeSummary explains private, review, publication-permitted and withdrawn states without implying publication or an original-file export grant. Missing video/audio playback retains a supplied description rather than presenting it as a transcript.

Route context requires an explicit action. Recorded/reported/estimated evidence uses solid/dashed/dotted patterns plus text; unknown geometry stays a gap. The current route specimen is a labelled illustrative diagram, not a geographical map. Source ownership, coauthor authority, publication permission and original-file export remain separate in every composition.

### Motion and extension

Use the shared feedback duration for immediate state feedback and reveal duration only when a transition explains continuity or intent. Reduced motion removes web transitions; the new native overlays require no animation. Do not add an unused variant to enlarge a catalog. Future screens need usable empty, error and loading states and a text-first route through their content.

## Do's and Don'ts

### Do:

- **Do** make chronology understandable with time, place, rest days and explicit uncertainty.
- **Do** reuse semantic roles and the canonical platform controls before adding a token or variant.
- **Do** preserve labels, drafts and chapter selection through pending states, failures and appearance changes.
- **Do** pair selected, review, error and route-evidence colors with visible text or non-color cues.
- **Do** keep ownership, coauthor authority, publication permission and original-file export distinct.
- **Do** label fictional samples and generated demonstration imagery honestly, with provenance.

### Don't:

- **Don't** place essential labels on photographs or unpredictable map backgrounds.
- **Don't** turn every section into a card, a metric hero or decorative cartography.
- **Don't** connect unknown geometry or present an illustrative route diagram as a geographical map.
- **Don't** use autoplay, scroll hijacking or 3D as prerequisites for reading.
- **Don't** describe session-only prototype changes as durable saving, contribution or publication.
- **Don't** treat screenshots, Metro exports or responsive web checks as Android or iOS runtime acceptance.
