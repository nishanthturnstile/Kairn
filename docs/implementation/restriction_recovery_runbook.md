## Independent journal

The reference service provides idempotent append by event ID, fsync before acknowledgement, ordered SHA-256 checkpoints, Ed25519 receipts, a nonce-bound signed current head, and a durable appender fence. Application workers receive raw **public** verification keys; private signing seeds remain on the independent host. Operator read/fence credentials and application append credentials are different. No HTTP delete, rewrite or truncate operation exists.

`FileRestrictionJournal` writes `restrictions.ndjson`, an acknowledged `journal-head.json`, and `appender.json` under an append lock. Fence/resume takes that same lock: a previously in-flight append either completes before the fenced head or is rejected. Resume requires an append credential that has never appeared in the retained generation history. Restart does not reopen the gate. A partial tail, missing acknowledged entry, signature/checkpoint conflict or abandoned append lock fails closed. Never remove a lock, truncate a file or lower a head merely to make startup pass; reconcile the external durable record and its uncertain append first.

The reference implementation bounds an event at 4 KiB, its log at 12 MiB and an authenticated snapshot at 16 MiB; exceeding capacity closes the boundary. Qualify capacity and a reviewed continuation/segmentation strategy before reaching those limits. Retain the log, verification/signing key ring and its independently recoverable checkpoints for at least 90 days **and** until every backup that can restore older rights has retired plus seven days. No automatic restriction/barrier GC is implemented without that proof.

Use pinned Node/pnpm and the committed backend build on the independent Linux host. Keep the journal volume, secret delivery and backups outside the application VPS and its restore set. Its loopback listener needs an independently configured HTTPS front door; do not expose the loopback HTTP listener directly.

1. Deliver a mode-0600 configuration file using the selected secret facility. Supply `directory` (absolute independent path), `port` (loopback port >=1024), `operatorToken`, a distinct `initialAppenderToken`, `keyId` and `signingSeeds` (key ID → base64url 32-byte Ed25519 seed). There are no supplied production credentials.
2. Run `pnpm journal -- initialize /absolute/private/config.json` once against a new empty directory. Remove the initial appender token from that host configuration afterward; retain the independently managed credential needed by the application generation.
3. Derive/distribute only the matching public keys to the application and operator verifier. `journalPublicKeys` exports the raw 32-byte public keys from the seed key ring. Do not copy `signingSeeds` to application configuration.
4. Run `pnpm journal -- serve /absolute/private/config.json` under the independent host's supervised service, bound to loopback behind HTTPS. Startup/configuration errors are generic; investigate private files locally.
5. Qualify retry of the same event after a lost response, signed fresh head retrieval, appender fence, restart while fenced, new credential admission, rejected old credential, retained-tail integrity, key recovery and independence from the application/object backup failure domain.

`HttpRestrictionJournal` requires HTTPS, rejects redirects, limits/timeouts responses and verifies receipt signatures, event hash, checkpoint chain and the fresh head nonce. The operator credential may read/fence/resume; an append credential cannot enumerate history or operate the fence. The API application has no history-deletion credential.

The cryptographic implementation uses Node's [Ed25519 signing/verification API](https://nodejs.org/api/crypto.html#cryptosignalgorithm-data-key-callback) and the key encodings in [RFC 8410](https://www.rfc-editor.org/rfc/rfc8410.html). The reference service's retained signing-seed ring is private independent-host material; recovery must preserve verification of every retained entry.

## Inventory and private operator files

Build the current committed application/worker images and retain their exact input/verification evidence. Recheck actual checkout/PR state before publishing a follow-up. Do not restore from an unqualified image or borrow an older verification result.

`pnpm recovery -- ACTION /absolute/private/operator.json` uses a separate controlled operator principal. Use a fresh external evidence directory for each drill; archive completed fence evidence privately instead of replacing a prior head in place. The application and worker never receive that URL. The private JSON supplies:

| Field | Meaning |
| --- | --- |
| `composeProject`, `composeFiles` | Actual single-VPS Compose project and absolute files declaring `edge`, `server` and `worker`. Inventory every additional scheduler/writer/appender before using this procedure. The current tool requires exactly those three declared containers at the fence. |
| `fenceDirectory` | Absolute maintenance/evidence directory outside the database/object restore set and redeploy automation. |
| `operatorDatabaseUrl` | Controlled connection to the application database with role-fencing/session-termination and migration/replay privileges. |
| `journal.endpoint`, `journal.token`, `journal.keys` | Independent HTTPS restrictions endpoint, **operator** credential and public verification key ring. The endpoint pattern is `/v1/restrictions`. |
| `newWriterPasswordsFile` | Separate mode-0600 JSON with `kairn_server`, `kairn_auth`, `kairn_worker` replacement credentials, each base64url 32–96 bytes (43–128 characters). Deliver through the secret facility; do not reuse the old generation. |
| `newJournalAppenderTokenFile` | Separate private text file for the next appender credential. Update the stopped compatible worker's private configuration with the same generation. |
| `releaseEvidenceFile` | Private JSON binding the independently verified head, source/image inputs and negative old-writer checks, described below. |
| `inspection` | Optional operator UUID, case UUID, purpose and operation UUID for an audited inspection. |

Do not paste secret files, SQL connection URLs, sealed mail, bearer credentials or object bodies into tickets/logs. The tools report generic failure and safe operation metadata. Preserve operator evidence privately under its declared retention.

## Fence, restore, replay and release

1. **Fence before taking the recovery head.** Run `pnpm recovery -- fence FILE`. The tool creates external `closing` evidence first, disables Docker automatic restart for the declared front door/API/worker, stops them, sets all three writer roles NOLOGIN and terminates their existing sessions. It records only container/image IDs and fence state. A missing inventory, running/restartable container or remaining writer session fails the action. Disable external redeploy/schedulers too; the script cannot discover an undeclared writer or another deployment system.
2. **Prove the old generation is fenced.** An already-connected old API/worker transaction must fail to commit; old credential reconnects must fail. Capture results and the fenced role/process inventory. If any writer or appender cannot be fenced, retain maintenance and stop the drill.
3. **Fence the independent appender and capture its current head.** Run `pnpm recovery -- head FILE`. The remote append lock drains/fences the old appender before the operator reads its signed fresh head. Keep the resulting `independent-head.json` outside the restore set. A busy/uncertain/corrupt journal is not a reason to assume the tail is complete.
4. **Restore the selected database/object checkpoint while closed.** Use the separately qualified backup tooling. Keep the edge/writers/redeploy controls outside the restore. Do not restore PostgreSQL global writer credentials from an old cluster dump; reapply the fence regardless. Preserve host-local signing/environment files and synchronize source by the [checkout workflow](checkout_workflow.md), never by transferring dependency/native output folders.
5. **Replay.** Run `pnpm recovery -- replay FILE`. It reapplies database fencing, verifies every signature/sequence/checkpoint against the independently obtained head and the restored replay checkpoint, then applies conservative denies. Missing resources receive opaque deny barriers. Version-2 account-deletion events retain only the opaque auth-subject/domain binding; replay reconstructs a deleting account tombstone and retirement even when the backup predates provisioning. Legacy signed bodies are never rewritten: replay requires their exact mapping or retirement to survive. A missing or conflicting legacy binding rolls the replay back and keeps recovery closed; never infer identity from email. Avatar barriers deny allocation, uploads, stale activation and managed reads. Invitations/transfers, archive/freeze/deletion and source/export restrictions cannot reopen. Account-derived administration freezes run in ordered batches before release. Replaying the same head is idempotent. A truncated/missing/corrupt/forked tail keeps all potentially affected delivery closed.
6. **Validate current objects and jobs.** Check the restored manifests/objects and managed read predicates; drain/reconcile stale work only through the compatible named worker operations. Account/owner denies dominate stale grants immediately; byte/PII cleanup and receipt confirmation are separate. The current clone drill covers invitation revoke, archive, transfer cancellation, last-admin departure, canonical/account deletion and source/export restrictions. Actual originals, caches, publication artifacts, ranges and stored answers extend this inventory in later workstreams.
7. **Rotate while still closed.** Run `pnpm recovery -- rotate FILE`. It requires successful replay and installs the new writer passwords while leaving NOLOGIN in place. Prepare exactly one compatible stopped container for each of `edge`, `server` and `worker`, set their restart policies to `no`, and mount their new credentials/private worker configuration. Old source processes must remain stopped/restart-disabled. Do not allow redeploy automation to reintroduce the previous environment.
8. **Supply release evidence.** The JSON must contain `sequence`, `checkpointSha256`, `oldWriterCommitRejected: true`, `oldWriterReconnectRejected: true`, `objectIntegrityVerified: true`, the exact 40-character `sourceCommit`, and `compatibleImages` containing the checked `sha256:` image IDs for all three containers, including the edge. These assertions require actual execution evidence; the tool does not create their truth by accepting a file. Qualify every newly added auth/publication/capture writer and credential before extending this inventory.
9. **Release deliberately.** Run `pnpm recovery -- release FILE`. It requires the rotated state, stopped, restart-disabled compatible edge/API/worker containers in the declared project and matching new database credentials on their respective API/worker services. It rechecks the remote fresh head, admits the replayed database boundary, resumes the independent appender with a different credential, starts the exact inspected API/worker container IDs and verifies their identities, image/environment inputs and health before starting the exact inspected edge ID. Release never runs Compose `up` or recreates a missing identity: changed Compose inputs cannot substitute a new container. Missing or failed checked containers keep release closed. Changes to mounted file contents remain part of the operator's qualified input evidence. Failure attempts to stop/fence the declared writers and appender again. Verify the old database and appender credentials remain rejected after release, and check fresh permitted/denied requests. Keep the front door closed if emergency fencing cannot be established.

The tool does not merge branches, weaken protection, publish an endpoint, restore a backup, retire backup generations or establish an independent provider. The actual destination/deployment drill remains mandatory before shared-data activation.

## Pending operations and support

`pnpm recovery -- inspect FILE` requires `inspection.operatorId`, `caseId`, a purpose from `support_case`, `incident_response`, `recovery`, `retention`, and `operationId`. The controlled transaction appends an `operator.inspect` audit event and returns only lifecycle/recovery state, revision, progress counts and a finite error code. It does not return a profile, source, sealed email, raw journal receipt or bearer status credential.

When the journal is unavailable, retain local deny and retry the same durable event. The 30-second named-worker reconciler continues after ordinary queue retries expire. Never re-enable a source/member/offer to make a pending operation look successful. Missing key/object/manifest/current-state evidence is a closed boundary, not permission to serve an older representation.

Post-deletion status is an ID plus separately retained hash-checked bearer credential with a hard 45-day limit and at most seven terminal days within it. No identity or source fields appear in that projection. Expiry/unavailability follows the support route; it does not restore account access or suspend backend recovery. Before enabling B04 account flows, retain the actual callback transaction guard, authoritative session checks, password policy and device/transport acceptance rather than treating this runbook as UI/auth sign-off.

## Opt-in worker mount

The base Compose foundation keeps domain workers unconfigured. A reviewed deployment override supplies `KAIRN_DOMAIN_WORKER_CONFIG` on `worker` and mounts its mode-0600 file at that exact container path with `:ro`. The host file must be readable by the image's non-root UID. Keep it outside the source tree/backup set as appropriate; do not add secrets to Compose YAML or a committed example. Qualify TLS SMTP, the private bucket and the independent endpoint before providing that override.
