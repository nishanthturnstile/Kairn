# Identity database foundation

This records the complete B02 schema/migration/privilege checkpoint (S01–S06). B03 extends it with the [transaction/worker boundary](domain_transaction_boundary.md), [recovery runbook](restriction_recovery_runbook.md), three opaque retirement/recovery records and migrations 0006–0008 (36 current tables). All 33 tables are modeled and migrated, including the five generated auth models, identity/avatar, canonical journey/admission/transfer, minimum source/export identities and durable operation/event/delivery state. B03 supplies the authorized command/worker, media, mail and independent-recovery implementations; B04–B08 supply their product flows. No authentication endpoint or account-deletion endpoint is enabled by this foundation.

## Ownership and policy graph

| Principal | Current identity authority |
| --- | --- |
| `kairn_migrator` | Owns schemas/tables and runs reviewed migrations. Explicit maintenance RLS policies apply. Only this controlled role can assume the provisioning owner. |
| `kairn_auth` | Library-required DML in `authn`; EXECUTE on the provisioning function; enqueue-only email partition access. No direct private-profile reads or domain writes. |
| `kairn_identity` | NOLOGIN, non-owner, no BYPASSRLS. Owns only the fixed provisioning function and must pass FORCE RLS. Can read/lock the required auth-user columns and provision the subject's account/profile. |
| `kairn_journey_policy` | NOLOGIN, non-owner, no BYPASSRLS. Owns fixed policy lookups and membership/graph triggers, with identifier/state/epoch column access only. No auth subjects, profiles or journey details. |
| `kairn_access_policy` | NOLOGIN, non-owner, no BYPASSRLS. Owns ten fixed boolean admission/source/export lookups. Column-only ID/state/epoch/revision reads; no auth subjects, profiles, recipient email, bearer hashes, storage keys or sealed payload. |
| `kairn_server` | Read current permitted journey/membership/capability rows through FORCE RLS; no journey writes yet. Read the active context account's permitted columns and private profile; update only its display name, bio and advancing profile revision. Enqueue-only access to the four approved product partitions. No auth-table access or provisioning EXECUTE. |
| `kairn_worker` | No identity-data authority yet. Can inspect the migration ledger/catalog for readiness; queue authority remains separately controlled. |

The API policy graph is `profile → account → transaction-local account UUID`. The provisioning graph is `profile → account → function-local verified subject`; the retired-subject lookup uses the same subject. Neither graph recurses into a protected membership table. The function has an empty `search_path`, qualified relations, restricted EXECUTE and a fixed local subject setting. The auth/API/worker roles cannot assume its owner.

Only trusted auth integration may call `provisionVerifiedAccount`, after resolving the library session. A UUID or subject supplied in request JSON is not an authenticated actor. The helper locks the auth user before looking up the domain account, rejects absent/unverified/retired subjects, and creates at most one account/profile. Repeated provisioning leaves the domain profile intact. Future coordinated retirement must follow that same auth-user/account lock order.

Domain references use the stable UUID in `identity.account`. Its nullable auth link is restrictive, not cascading. Detachment requires a retired-subject barrier; the barrier has no live-auth FK and survives an auth-user purge. The transition trigger prevents reactivation and requires advancing revisions/generations. These constraints support future lifecycle work; they do not implement journal-confirmed deletion or restore replay.

`runAsAccount` owns one checked-out connection and a real Drizzle transaction. It installs transaction-local account context and checks current account state/revision/generation before invoking the typed operation. Nested transactions use savepoints and remain part of the outer atomic unit. A final SQL probe rejects a swallowed SQL failure before PostgreSQL could silently turn COMMIT into ROLLBACK. COMMIT/ROLLBACK clears context; any failed operation discards its connection, including rollback/socket failures. Future complete domain operations must add their resource lock order, authorization, receipt, audit, queue and response-generation checks inside this boundary.

## Canonical journeys and membership reads

Migrations `0002_journeys_foundation.sql` and `0003_journeys_access.sql` add one canonical journey, a stable unique `(journey_id, account_id)` membership across all states, and explicit membership-epoch capabilities. The composite capability FK binds membership and journey. A partial unique index permits at most one active administrator; deferred constraint triggers require exactly one for nonterminal assigned journeys and validate the complete current capability graph at commit. Zero administrators require an explicit freeze or deletion. Ended memberships keep their latest prior power snapshot; rejoining advances the epoch once, clears that snapshot and cannot reactivate old capability rows. The old rows remain revoked history. These are database invariants, not invitation acceptance or command implementations.

The current read policy is:

| Actor | Journey details | Membership/capability rows |
| --- | --- | --- |
| Active administrator | Current active/archived journey | Active roster and its current powers, plus own history |
| Active participant, coauthor or publisher | Same current journey, regardless of which independent power is held | Own membership/power history and the current administrator |
| Former member | None through the journey table | Own minimal participation and power history only |
| Outsider or missing account context | None | None for other accounts |
| Restricted/deleted account | None | None |

Creator identity alone grants no access. Canonical deletion denies the detail row even to its creator and retains only opaque membership references. The API projection layer must still construct the declared limited/admin/former wire shapes; these raw tables are not HTTP response schemas. Profile data remains private under its existing independent RLS graph; permitted display identities need a separate scoped projection in later work.

Runtime RLS calls three fixed, empty-search-path, SECURITY DEFINER boolean lookups. Their non-login owner receives SELECT only on required identity/journey IDs, lifecycle/state and membership/capability epochs, plus journey-ID UPDATE solely for the graph trigger's row lock. Its explicit UPDATE policy has a false WITH CHECK, so it cannot change rows. All helper reads themselves pass FORCE RLS through role-specific policies. The acyclic helper policies do not call runtime membership policies; runtime roles can neither assume nor inherit the helper role. Auth/worker have no journey-schema access. Catalog readiness rejects excess helper columns, runtime DML, missing/disabled integrity triggers, unsafe helper functions and missing administrator uniqueness. The protected policy fingerprint rejects changed or additional policies.

The graph check locks the canonical journey row before checking committed constraints. B03 coordinators acquire journey, membership and capability locks in that order before changing them, end membership before revoking its capabilities, and perform current authority/generation checks with their atomic receipts/audit/restriction records. The API retains direct SELECT grants on these three tables; checked B03 functions own mutations. Freeze and archive cannot be reversed through ordinary updates; separately authenticated/audited orphan-administration recovery is still pending.

Journey fields store the intended local minute, UTC instant, IANA context and signed offset. SQL validates that both start/end instant/offset pairs map to the supplied local minute, including DST transitions, and rejects partial tuples/reversed time. Title/time details may be purged on a deleted tombstone; restrictive FKs preserve canonical and actor references. This does not yet implement retention workers or deletion confirmation.

## Complete S02–S06 database boundary

The final B02 release adds `0004_complete_domain_foundation.sql` and `0005_complete_domain_access.sql` without changing applied `0000`–`0003`. The first defines 22 additional tables, the owner-bound profile avatar reference, verified avatar bounds, typed operation targets, service/operator audit identity and retained-history FK indexes. The second installs transitions, read policies, fixed helpers and explicit runtime ACLs. Declarative models and Drizzle snapshots reproduce the final 33-table schema with no drift.

| Concern | Tables / invariant |
| --- | --- |
| Avatar | `identity.profile_avatar`; one available and one pending replacement per owner, private quarantine/representation locations, verified input dimensions at most 12 MP, output at most 512 per side without upscaling, finite failure state, bounded upload lifetime and owner-bound profile selection. Recorded metadata does not prove real decoding/re-encoding. |
| Admission | `journeys.recipient_guard`, `invitation`; unique journey/opaque recipient, immutable known-account binding, epoch/end barrier, one pending offer, hash-only secret, immutable proposed coauthor/publisher powers and seven-day expiry. Departure invalidates every prior pending offer; reissue differs from resend. |
| Administration | `journeys.administration_transfer`; one current offer, composite membership/journey/account bindings, captured epochs/generation and 72-hour expiry. Only a current active coauthor can accept. Commit must move administration and advance generation. A fresh archive-aware continuity transfer is allowed; stale pre-archive offers are invalidated. |
| Source identity | `sources.source`, `source_asset`, `source_grant`; immutable source/owner/provenance and asset/source/owner association, original-purpose assets separate from avatars, one current source/journey grant, bounded states and advancing revisions. Registration is not verified byte availability. |
| Exact export | `sources.export_request`, `export_request_asset`, `export_grant`, `export_grant_asset`; one to 100 explicit assets, recipient membership epoch, exact source/owner/journey relationships and immutable requested/issued revision snapshots. FK snapshots terminate at immutable request bindings, never at mutable current source-grant revisions. Withdrawal remains possible. |
| Command/impact | `operations.command_receipt`, `impact_preview`; actor/command identity and normalized digest, finite operation/result kinds, retained expired identity barriers, hash-only five-minute actor/action/target/version-bound previews and one-time consumption. No arbitrary saved request/response JSON. |
| Operations/recovery | `operations.lifecycle_operation`, `restriction_event`, `restriction_delivery`, `restriction_receipt`; immutable event identity/integrity, monotonic progress, finite retries, matching immutable receipt before confirmation and per-operation receipt completeness. Cleanup completion and recovery confirmation advance separately. Deletion-status hashes are private; hard expiry is at most 45 days and terminal availability at most seven days within it. |
| Safe events/cursors | `operations.audit_event`, `account_notice`, `domain_change`; finite actions, account or named service/operator identity, purpose/case-bound operator metadata, recipient-safe notices, immutable opaque changes and scoped monotonic cursors. No source text, credentials, email bodies or coordinates. |
| Delivery/budgets | `operations.email_delivery`, `abuse_counter`; token/offer-bound expiry, bounded authenticated-encryption envelope fields, irreversible payload purge/terminal state, HMAC target keys and bounded counter windows/retention. B03 implements encryption, atomic budgets, SMTP retry/current-token checks and bounded cleanup; B04 integrates the actual account flows. |

Admission invalidation runs on membership end, loss of administration/coauthor transfer eligibility, archive and freeze. Acceptance validates current account/membership/epoch/authority and expiry. It cannot revive terminal offers or widen a pre-existing membership through an ambiguous invite. The database permits no ordinary rebound of a known recipient to a new account, even if an email is reused. Bound identity remains an opaque tombstone after recipient PII is purged.

Source read policies distinguish ownership from editorial power. Owners retain their private current sources; active coauthors/publishers see only currently granted review/publication-reuse sources in their journeys. Administration alone and ordinary participation grant no review access. `sources.actor_can_export_asset` checks the exact active approval, asset/source/owner/journey identities, verified asset revision, each current source-grant revision, live owner/recipient state, membership epoch and clock-time expiry. It denies old grants after withdrawal, asset revision change, departure/rejoin or owner-account denial. It is a database predicate for later B03 service integration, not a download endpoint or proof of actual stored bytes.

The acyclic policy graph is `runtime row → fixed boolean helper → column-bounded lookup policies`. The access helper reads required policy inputs through its own FORCE RLS policies; those policies never recurse into runtime policies. Operation policies instead follow `receipt/delivery → restriction event → lifecycle operation → own active account`, with source/journey predicates for scoped audit. No normal login can assume or inherit either lookup owner. Avatar locations, invitation/impact/status hashes, recipient email/key, notice target fields and sealed mail are not granted to ordinary API reads. Email/counters and all new domain data remain inaccessible to the worker/auth role until named trusted operations are qualified.

At the B02 checkpoint (0000–0005), new domain writes were deliberately closed. The API has read grants plus append-only INSERT ACLs for audit/change/restriction records with explicit false write policies. It cannot update/delete those records, write other new tables, or bypass RLS. B03 now supplies reviewed narrow handlers with current authorization, command reconciliation, receipt/audit/notices/change/event/job atomicity and denied-enqueue rollback tests; the extension below records that change. The B02 checkpoint included own-profile update and four enqueue-only producer paths; B03 moves profile writes behind its command boundary. This is a complete schema/privilege foundation, not an activated command implementation.

Coordinators lock canonical journeys in UUID order, then affected memberships/recipient guards and sources/grants in stable UUID order. End membership before revoking its capabilities so the prior-power snapshot is captured. Advance the admission guard before issuing a replacement offer. Mark transfer acceptance before replacing the administrator in the same transaction, then advance the journey generation; deferred validation observes the final assignment. Account-wide work first denies the account, then uses bounded ordered units. Worker job JSON remains an event reference; it cannot install arbitrary account context. B03 qualifies named worker access and introduced command/confirmation/cleanup races; later capability/admission races accompany B06/B07 activation.

G03 and the B02 FK/unique/non-owner isolation checks use a disposable PostgreSQL database. The 18 integration scenarios include supported two-/four-migration upgrades with retained data, failed pending-release rollback, fresh/repeated packaged bootstrap, five-member capability/source fixtures, admission uniqueness/end/rejoin, accepted/archive transfer, avatar ownership/bounds, exact-export cross-bindings/snapshots/100-asset bounds, safe operation/mail metadata, retention barriers and readiness drift. A real EXPLAIN uses 120 memberships across two accounts and a 20-row ordered keyset page; it uses `membership_account_history_idx`. Every domain FK has a nonpartial index starting with its leading key. This is representative query-plan evidence, not a production throughput benchmark.

## Generation and controlled execution

Schema definitions are in `packages/backend/src/identity`, `journeys`, `sources` and `operations`; shared schema checks and catalog readiness stay within the backend; reviewed SQL, Drizzle snapshots and the SHA-256 manifest are in `packages/backend/migrations`. The backend build copies only runtime SQL/manifest, excluding authoring snapshots. `tools/identity-generation` owns the pinned offline Better Auth/Drizzle generation graph. It is absent from production dependency closures.

```sh
pnpm auth:schema:generate  # Regenerate from the pinned shared auth options.
pnpm auth:schema:check    # Detect generator/configuration drift.
pnpm db:generate         # Generate the next Drizzle SQL/snapshot for review.
pnpm --filter @kairn/backend db:manifest # Refresh checksums only after reviewing SQL.
pnpm verify:identity     # Disposable PostgreSQL project/volume; never the development DB.
```

The one-shot `migrate` service runs identity migrations before the existing controlled pg-boss bootstrap. The identity runner serializes with a database advisory lock, verifies every SQL checksum and applied ledger entry, and applies the pending release in one transaction. Failure rolls back the whole pending release. Changed SQL, unsupported newer versions, missing policies, unsafe role ownership/privileges and missing grants block readiness. The final applied ledger entry records a SHA-256 fingerprint of every supported identity/journey/source/operation policy's schema, table, name, permissiveness, roles, command, USING and WITH CHECK definition. Readiness, repeated migration and the start of an upgrade compare the complete catalog with that protected baseline; they never adopt changed or additional policies on a repeat. Deparsing uses a transaction-local fixed search path on one connection. Runtime never migrates. The existing two-migration identity checkpoint is a supported upgrade input, alongside a fresh queue-only database. Before adding the journey policies, the runner compares the original identity-only fingerprint using its original JSON representation; the journey checkpoint covers identity/journeys; the completed B02 entry covers identity/journeys/sources/operations. The original four-migration journey checkpoint is also a supported upgrade input. Applied SQL/checksums are unchanged.

For an existing foundation volume, stop Compose Watch/builds and the API/worker first. Keep the volume. Recreate only the PostgreSQL container from current Compose inputs so it receives the new read-only principal script and `KAIRN_AUTH_DB_PASSWORD`; a healthy database does not re-run new-volume initialization. Then run the explicit controlled principal step, followed by the normal migration/build/start:

```sh
docker compose stop server worker
docker compose up -d --no-deps --wait postgres
docker compose exec -T postgres psql --username postgres --dbname kairn --set ON_ERROR_STOP=1 --file /etc/kairn-postgres/identity-principals.sql
docker compose up -d --build --wait
```

The principal script creates absent auth/provisioning/journey-policy/access-policy roles and explicitly sets the auth credential from the container environment. It does not reset existing server/worker credentials or drop data. Supply the intended host-local auth credential before using it. Runtime images never receive the migration-owner secret. Application rollback is allowed only to a schema-compatible image; do not edit applied SQL or drop domain data to undo application code.

Declaring the function-local custom setting needs PostgreSQL's narrow [SET parameter privilege](https://www.postgresql.org/docs/18/sql-grant.html). Controlled bootstrap grants it only to the migrator and provisioning owner, without granting runtime DDL or superuser authority.

## Pool budget and qualification scope

The current API pool has four connections. The worker has four pg-boss connections plus one readiness connection. The migration unit has one identity/DDL connection and one pg-boss bootstrap connection, so the configured maximum with all three units overlapping is eleven. The future auth runtime/producer pools are not instantiated; their bounds must be added before B04 activation. PostgreSQL administrative/recovery and test connections require separate headroom. Readiness uses the same supported identity/queue checks in both application processes.

## Enqueue-only product queue boundary

Controlled bootstrap pre-creates `kairn.email.v1`, `kairn.restriction.confirm.v1`, `kairn.lifecycle.cleanup.v1` and `kairn.identity.avatar.v1`, each using standard policy, a dedicated partition and polling (`notify: false`). It resolves the actual table name from pg-boss metadata and quotes it as an identifier. Queue creation is idempotent; incompatible existing policy/partition/notification settings fail. ACL installation uses one checked-out connection/transaction after creation; a failed phase blocks startup and can be repeated.

The API role receives INSERT and SELECT of `id` only on the four approved partition tables. Auth receives the same rights on email only. Both may read queue/version metadata and execute `pgboss.job_now()`, as required by pinned `pg-boss@12.38.0`'s real insert SQL. Neither receives payload reads, job UPDATE/DELETE, sequence rights, worker functions, queue administration or shared/unapproved table inserts. Worker permissions remain separate. Readiness checks the complete producer ACL boundary, actual partition-parent relationship and required queue configuration; missing and excess rights fail closed.

`startJobProducer` accepts one caller-owned bounded metadata pool and returns four named enqueue methods plus shutdown. Configure a single one-connection metadata pool shared by process callers; do not create it per request or send. Migration, supervision, scheduling, instance registration, persisted warnings/statistics, reindex and LISTEN/NOTIFY are disabled. The factory handles idle metadata errors while active and leaves pool shutdown to its owner. No application entry instantiates it yet, so this slice does not increase the current eleven-connection maximum. B03 keeps the worker readiness pool separate from its two-connection domain pool. The integrated allocation is API domain four, auth two, shared producer metadata one, worker domain two, queue four and readiness one: fourteen runtime connections, or sixteen including the one-shot migration overlap, plus explicit operator/test headroom.

Every send uses `fromDrizzle(transaction, sql)` on the supplied real domain/auth transaction; the factory never dispatches a write through the metadata pool. Payloads contain only a stable event UUID reference; no recipients, tokens, mail bodies or account impersonation context. The same UUID is the job ID. A duplicate returns `inserted: false`, which is not proof of an equal command payload or current authority. B03 resolves durable command/event identity and atomically adds audit/notices/generations with this boundary. Named handlers, live target validation, sealed delivery, the pinned auth-callback transaction guard and restriction confirmation/replay are implemented in the linked boundary. Actual off-host deployment and the product auth/HTTP flows remain separate gates.

`pnpm verify:identity` now includes two producer scenarios on its own disposable PostgreSQL volume after the five identity scenarios. They exercise actual API/auth transactions, allowed sends, denied enqueue rollback, payload/consume/admin/unapproved-partition denials, ID deduplication, excess-grant readiness rejection and restart/consumption through the actual worker role. This is the producer portion of G08; it does not close the later command/audit/event/mail-callback acceptance gate.

## Declaration and production packaging

Drizzle's strict declaration graph reaches other dialect declarations. The exact `gel@2.2.1` and `mysql2@3.24.6` development peers satisfy those published type imports; neither is a selected runtime database driver. Declaration-only Drizzle/Gel patches retain strict checking and Node-only globals. The compiled transaction consumer includes negative checks for invalid profile revisions and invented credential fields. Preserve and requalify these repairs with upgrades.

The pinned pnpm `12.16.1` default production deploy fails when its dedicated lockfile prunes the patched development-only Gel peer but retains that patch hash inside Drizzle's identity. Production image stages therefore use the supported [legacy deploy path](https://github.com/pnpm/pnpm/blob/main/pnpm/docs/cli/deploy.md) with `--prod --frozen-lockfile`. `allowUnusedPatches=true` is scoped to those deployment commands because the source workspace also contains native/declaration patches absent from production. The normal Docker dependency stage still installs the full source workspace with frozen patch/config checks and no such override; an altered-patch fixture must fail there. Included patches stay applied, production closure probes reject the generator and unused Gel/MySQL drivers, and the source lockfile is never rewritten by packaging. Requalify this workaround when pnpm changes.

Executed results and actual source/image inputs belong in [implementation progress](accounts_journeys_access_progress.md), including failures. This document describes the boundary; it is not acceptance evidence by itself.

## B03 runtime extension

B02's closed writer policies remain in place for direct application DML. `kairn_command` is a separate non-owner NOLOGIN service principal; only explicitly checked entry points are executable by API/auth/worker roles. Direct profile writes are also revoked. Readiness checks policy fingerprints plus the protected function/ACL/table/column/index/constraint/trigger fingerprint stored in the release ledger. The new `retired_avatar` prevents UUID reuse after byte/manifest purge; `recovery_barrier` retains denies for resources absent from a restored checkpoint, and `recovery_checkpoint` records ordered replay progress. All three use FORCE RLS and closed runtime table ACLs.

Before applying the B03 release to an existing volume, rerun the controlled `identity-principals.sql` step to add `kairn_command` with non-inherited migrator SET permission. Preserve existing application credentials and data. The current default API/queue/readiness maximum remains nine runtime/eleven with bootstrap; the opt-in domain worker adds two (eleven/thirteen). Account auth and shared producer metadata add the remaining three at B04 activation. No developer volume or native checkout was upgraded by the isolated tests.

See the transaction boundary for exact commands, private media limits, callback handling and retention; see the runbook for independent journal credentials, writer fencing, replay and qualification limits. A complete B03 foundation does not enable ordinary unfreeze, account UI, capture delivery or shared data.
