# Competitor architecture evidence

Historical first-pass research. Recommendations may be superseded by the current architecture. The sole current stack/dependency register is [architecture section 14](../../core/architecture.md#14-canonical-stack-and-dependency-register). This file is evidence, not an install list.

Research date: 1 November 2026. Scope: every named competitor, substitute, and adjacent file ecosystem in the product plan and requirements.

## Evidence rules

- A first-party careers page, technical credit, or processor list can confirm the technology it actually names. It does not establish the complete stack, deployed versions, schema, scaling limits, or security effectiveness.
- Product help can establish documented behavior. The architectural consequences below are our inferences for this product.
- No authenticated competitor workflow, application binary, private endpoint, or production reliability was tested. No technology-detection vendor is treated as authoritative.
- Confidence is high for directly quoted technology names and documented controls, medium for inferred design lessons, and unknown for private implementation details. All stack versions remain unknown unless a source explicitly names them.

## Source conflicts and limits

RouteTale's import documentation says it does not connect directly to Strava, while its privacy policy refers to connected Strava credentials. Treat the precise integration status as unresolved. Neither source should be used to promise an equivalent integration here.

The current [Strava API policy](https://www.strava.com/legal/api_policy) contains detailed restrictions on API data and AI-related uses. This is a source to review before any future API integration, not legal clearance for user-uploaded files or an assertion that all manually uploaded data is API data. The approved R1 manual-file approach avoids a direct integration dependency. Seek terms review for the actual data origin and proposed use.

The product docs previously recorded failed fetches for TrekYatra and TrailScout. Both pages were readable in this pass. Their product claims remain marketing evidence, not proof of reliability, adoption, current safety, or private technology.

No source supports inferring that all competitors use microservices, event sourcing, CRDTs, a vector database, or a particular AI vendor. A PostgreSQL-backed modular application with workers is a design choice for our requirements, rather than a claim about their internals.

## Architectural lessons supported by the comparison

1. Keep one canonical journey identity and distinct membership references. Published collaboration demonstrates demand for shared editing, but does not reveal a competitor's schema.
2. Build durable offline capture and resumable synchronization explicitly. A network query cache alone cannot protect a saved camera file.
3. Store raw recordings independently of map display geometry. Import restrictions and map-oriented simplification must not destroy source evidence.
4. Use revision-aware edits and retained conflicts. R1 does not require character-level live coediting.
5. Separate readable story delivery from heavy maps and media processing. Map playback and exports are optional capabilities around the core narrative.
6. Treat revocation, derivatives, old publication URLs, and answers as one dependency problem. Listed competitor services do not establish that they solve this problem in the same way.
7. Use MapLibre/PMTiles and React/React Native as evidence-backed candidates. Choose exact packages on compatibility, licensing, operational cost, and product fit, not imitation.

## Research method

Five focused web-search rounds located first-party technology evidence. Direct source opens then checked product behavior, credits, roles, and processor descriptions. Secondary job aggregators and technology fingerprints helped discovery only and are excluded from stack confirmation. The linked primary pages are the evidence record; no inaccessible private architecture is reconstructed.
