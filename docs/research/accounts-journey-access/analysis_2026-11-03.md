Important code observations:

- `apps/server/src/app.ts` currently accepts a single browser origin and advertises only GET/HEAD in preflight handling. Adding auth and writes requires deliberate middleware ordering and exact origin/method/header handling. A blanket wildcard or disabled CSRF check is not a solution.
- That server currently renders the creator shell only at `/` and `/setup/status`; real account/journey deep links also need an explicit route fallback that cannot swallow API/auth/asset failures.
- `packages/contracts/src/client.ts` deliberately requires an injected transport. This is the existing seam for browser credentials and awaited native cookies; keep it instead of introducing a second HTTP client.
- `packages/backend/src/database.ts` checks the queue version, not domain migration readiness. Extend readiness when actual domain migrations exist.
- `packages/backend/src/queue.ts` disables runtime migrations. Preserve that separation when adding Drizzle and auth tables.
- Web creates a QueryClient per router. Native currently has only the system-status query. Neither demonstrates authenticated cache isolation or stale-response handling after logout.
- Native uses system fonts pending font delivery. Web names the selected families but does not ship their binaries. Token strings are not evidence that typography is implemented.
- The current native scheme is `kairn-dev`, bundle/package ID `dev.kairn.app`. Preserve development identifiers until the separate permanent-name/domain decision.

## 3. Functional analysis

The first product outcome is: a person signs in, creates a private journey, invites another person, and both open the same canonical ID with explicit, different rights. Several roles still produce one history entry. Removing access stops protected use and records both the user-visible effect and recovery-confirmation state.

| Module | User problem | Required boundary |
| --- | --- | --- |
| Identity and recovery | Return to the same account on web, Android and iOS. | Better Auth authenticates; domain account identity survives role changes and never derives from an email match alone. |
| Profile and sessions | Choose a display identity and control signed-in devices. | Email/session details stay private; avatar/media exposure is explicitly scoped. |
| Canonical journeys/history | Find one event regardless of several roles. | One journey row and one account/journey membership reference, including minimal former-member history where permitted. |
| Invitations | Join the intended group without exposing a gallery. | Verified recipient, expiry, single-use/replay rules, existing journey identity, no access before acceptance. |
| Membership/capabilities | Understand and change actual powers. | Active administration, coauthoring and publishing are independent; contributor ownership is not an administrator-assigned role. |
| Source grants | Choose review or publication reuse. | Owner-controlled grant per source/journey, current revision, absent grant means private. |
| Original exports | Allow named people to obtain exact original files. | Separate grant, exact assets, recipient membership, source revisions, expiry and current download checks. |
| Lifecycle | Leave, transfer, archive or delete without surprising the group. | Separate impact previews, accepted transfers, no-successor freeze, current-state confirmation and bounded operations. |
| Audit/notices | Explain changes without broad access to private material. | Minimal immutable audit; recipient-specific, sanitized notices and scoped change records. |
| Restriction recovery | Keep revoked access revoked after a restore. | Immediate local deny, independent durable receipt, stable retries, completeness-checked replay. |

Transfer and departure have richer source/editorial effects in delivery step 4. Basic membership/administration lifecycle cannot be postponed after active memberships are introduced. The same principle applies to account deletion and any profile asset introduced now. Full source workflows, original archive generation and managed downloads remain explicitly tied to the later data workflows that make them usable.

## 4. Integration research

### 4.1 Better Auth and native transport

Context7 resolved `/better-auth/better-auth` and supplied the exact `v1.7.15` index matching architecture. Its [documentation version index](https://better-auth.com/llms.txt) identifies the 1.7 documentation line; tagged source is the exact-pin reference.

The selected [Expo integration](https://github.com/better-auth/better-auth/blob/v1.7.15/docs/content/docs/integrations/expo.mdx) stores native session material through SecureStore. At this version, `getCookie()` is asynchronous; custom authenticated fetches await it and use the documented manually attached Cookie transport with `credentials: "omit"`. Browser transport uses cookies instead. Plan native rebuilds and real requests rather than treating a successful JavaScript import as qualification.

Version qualification is specific: the tag matches Better Auth 1.7.15, while the guide's example baseline is Expo SDK 55. It explicitly calls for SecureStore and Network; some Linking/WebBrowser/Constants guidance concerns optional social flows. Kairn's SDK 58 graph and selected email/link behavior need their own integration/build/device checks. Do not describe the guide as a qualification of that full stack or install optional social-flow dependencies indiscriminately.

The [Drizzle adapter documentation](https://github.com/better-auth/better-auth/blob/v1.7.15/docs/content/docs/adapters/drizzle.mdx) supports PostgreSQL schema mapping. Generate the auth-owned schema from the actual pinned configuration and review its SQL; do not hand-copy a generic auth model, enable unrelated plugins, or install Better Auth infrastructure services from an example. The domain profile and journey model remain separate.

Version-matched Context7 results also show verification/reset callbacks. Use the selected Nodemailer/pg-boss interface, with Mailpit locally and Resend at deployment. Callback success, auth-row commit, and durable email enqueue are separate failure boundaries that need actual integration tests. Do not claim a library callback automatically joins the domain transaction.

### 4.2 Drizzle migrations and RLS

Context7 resolved the exact `/drizzle-team/drizzle-orm/0.45.4` source index. It documents migration-ledger configuration and PostgreSQL policy declarations. Current [migration guidance](https://orm.drizzle.team/docs/migrations) distinguishes generated SQL migrations from direct schema push. Kairn selects reviewed committed SQL with controlled execution; live 1.0-era examples do not upgrade the pinned 0.45.4/0.31.11 pair. Verify the node-postgres migrator and release runner at installation rather than copying a postgres.js example.

[PostgreSQL 18 row-security documentation](https://www.postgresql.org/docs/18/ddl-rowsecurity.html) confirms default denial after RLS is enabled without applicable policies and the owner/superuser/BYPASSRLS exceptions. Therefore runtime identity must be non-owner, policy paths must be tested under that actual role, and membership-policy recursion needs explicit design. Application authorization still controls action semantics and response fields.

Use transaction-local account context: PostgreSQL's [configuration-setting functions](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADMIN-SET) provide the local-setting boundary. Resolve the verified identity before entering the transaction; never trust an actor ID in JSON. Test pooled-connection reuse and missing context. A session-level setting can leak across requests.

Index foreign keys and the actual permission/history joins. Review consistent lock order, current-state checks, composite relationship integrity and restrictive-versus-expansive concurrency. Avoid time-dependent partial-index predicates such as `expires_at > now()`; compare expiry at use time.

### 4.3 Transactional jobs and email

Context7's pg-boss resolution returned a secondary DeepWiki entry and an unrelated wrapper. Neither was used as technical authority. The first-party [pg-boss 12.38.0 adapter page](https://pgboss.io/api/adapters#drizzle) explicitly supplies `fromDrizzle(tx, sql)` for atomic job enqueue. Use the existing selected pg-boss, not a new outbox/dispatcher or wrapper package.

Domain writes, audit/change records and jobs can share that transaction; network delivery cannot. Retry workers must check current invitation, token expiry, account state and generation before sending. External effects remain at least once. No recovery URL, invitation token, password, session secret or email body belongs in logs or ordinary notice payloads.

### 4.4 Query and routing

Context7 resolved `/tanstack/query`; its listed versions did not include the selected 5.105.1 patch. Treat its core-source results and the official [v5 QueryClient reference](https://tanstack.com/query/v5/docs/reference/QueryClient) as behavior guidance, with installed-version acceptance still required. Cancellation/removal differs from invalidation: invalidation retains cached data. Logout/revocation must remove protected state and reject late responses, not merely schedule a refetch.

Keep typed wire contracts and the injected fetch boundary. Route guards prevent a confusing screen transition; the server remains authoritative. Route hydration must not briefly show a prior account or discard a cold-start invite intent.

### 4.5 Design, fonts and accessibility

The existing design is already specific: warm Paper, Forest actions, restrained Clay review states, Newsreader editorial type, Instrument Sans controls, approved journey media and an evidence-respecting journey line. A new generic dashboard or decorative travel hero would obscure that direction. This milestone's account/People/forms are task-oriented; journeys and empty states carry the quieter editorial character.

The upstream [Newsreader license](https://github.com/google/fonts/blob/main/ofl/newsreader/OFL.txt) and [Instrument Sans license](https://github.com/google/fonts/blob/main/ofl/instrumentsans/OFL.txt) are published as SIL OFL 1.1. Record the exact downloaded artifacts, hashes, notices, weights and embedding choices during asset delivery; finding a license does not mean the binaries are bundled or a legal review was performed.

A planning calculation using the committed sRGB colors found Ink 500 on Paper 0 approximately 5.15:1, Forest 800 9.17:1, Clay 800 7.62:1, and Clay 500 3.56:1. These are nominal token checks, not rendered accessibility evidence. Clay 500 is unsuitable for normal small text. Line 200 on Paper 0 is only about 1.36:1: decorative separators can use it, but a required control boundary needs a stronger approved token or another compliant affordance. Validate every interactive state and image overlay during implementation.

Review follow-up: Clay 500 directly on Forest 800 is about 2.57:1. Required focus on that actual adjacency needs a contrast companion; the existing design specifies a Paper 0 offset, so the direct pair alone does not establish a current focused-button defect. The handoff now maps enabled borders to Ink 500 and specifies light/dark focus treatments from existing colors, pending rendered acceptance.

The W3C [accessible-authentication explanation](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html) supports password-manager and paste assistance. The [focus-not-obscured explanation](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) matters for sticky actions and dialogs. These translate into autofill/paste support, visible persistent labels, error focus, keyboard-safe actions, focus restoration and assistive-technology checks, alongside the project's larger target sizes.

## 5. Main risks and planning consequences

| Risk | Consequence for implementation |
| --- | --- |
| Treating setup database bootstrap as domain migrations | Add actual schema-version/readiness and upgrade/replay gates. |
| Conflating member, admin, editor, publisher and owner | Centralize the capability matrix and expose safe action-specific affordances. |
| Loose source/asset/journey references | Use relational constraints plus transaction-time owner/revision checks, including multi-source export batches. |
| Auth deletion cascading directly into shared records | Domain lifecycle coordinates denial, transfer/freeze and purge; disable/restrict bypass paths. |
| Invitation replay reactivating a removed member | Consume once; old receipts cannot grant new rights; reinvitation is a new explicit operation. |
| Rejoin reviving old capabilities or recipient export grants | Advance membership epoch, install explicit rights and permanently invalidate grants from the prior participation epoch. |
| FK from an export snapshot to a mutable source revision | Compare the issued snapshot at use; never let referential integrity prevent narrowing/withdrawal. |
| Expansive write racing a revocation | Lock/recheck generations inside the same operation and keep stale jobs from restoring access. |
| Journal destination still unselected | Local interface/failure drills can proceed; independent recovery completion cannot be claimed. |
| Grant schema declared finished without capture/export integration | Record foundation completion separately from later source/export user acceptance. |
| Retaining private cached data after denial | Remove protected query/route data and fence in-flight responses. |
| Applying generic skill defaults | Keep Unistyles, light-first tokens, Lucide, local builds and Vite+; no NativeWind, @expo/ui, Expo Go or extra tool stack. |
| Consumer UI treated as final decoration | Deliver composition/state specs and primitives before feature screens, then verify real tasks. |

## 6. Research limits and next decisions

No runtime dependencies, schema, migrations, credential settings, native projects or application code changed for this research. No new auth, SQL policy, device or recovery check has passed by virtue of this document. The existing setup/native acceptance remains valid only for its documented inputs.

At the original research point these choices were open. Version 1.2 now selects the authority/roster, field/expiry/retention, category/time and visual-input baseline explicitly. Actual independent journal destination/access and production domain/sender remain external integration inputs. Existing requirements settle the main workflow and sign-in method, so those are not reopened as preference questions.

The recommended first build is the design/component handoff plus migration/policy contract. Then deliver real account recovery and a private create/join journey flow. Shared-data expansion remains closed until the independent restriction boundary is qualified. Capture, imports, publication and discovery continue through the remaining R1 delivery steps.
